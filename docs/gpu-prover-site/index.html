A GPU path for the midnight-proofs prover

midnight-proofs proves PLONK circuits with KZG commitments over BLS12‑381. Built with the feature gpu, it can run its heavy arithmetic on a CUDA device. The proof system, the keys, the transcript and the verifier stay as they are.

The device takes the G1 multi-scalar multiplication (MSM), the number-theoretic transform (NTT), its inverse, and the quotient. An accepted quotient call does all of its work on the device: the cosets on the extended domain (a coset of a larger evaluation domain), the numerator, the division by Xⁿ − 1 and the inverse transform back to coefficients. The prover reaches each of the four through a hook: a function that it calls in place of the CPU routine. A hook returns exactly the value that the CPU routine returns, or it declines, and then the CPU routine runs on the unchanged input.

A resident daemon holds the SRS (the structured reference string, the public KZG parameters) and the proving key between requests. By default it frees its device copies of the key and its MSM base tables before each reply and uploads them again for the next request. Before a proof that may use the GPU, the daemon checks the device memory. On a native Linux host, the daemon first activates the device and then reads its free memory. If it gets no reading, it counts zero bytes free. Under WSL2 it uses a leased budget. It compares that figure with its estimate, and individual device calls can still decline. When the request ends it overwrites every witness-dependent device and staging buffer with zeros and confirms the cleanup; if it cannot confirm it, the daemon retires. It verifies every proof before it returns it.

Try it

The daemon and its client build with cargo. These commands serve the example relation of the crate with a test SRS and make one proof. Build with the feature cuda to route proof phases to a CUDA device. Without a CUDA compiler the same command still builds, and the daemon proves on the CPU. The example circuit is small, below the size from which the device takes work by default, so this run checks the service and not the kernels. 

cargo build --release -p midnight-gpu-prover --features cuda
P=target/release

# The socket lives in a fresh directory that only you can enter.
D=$(mktemp -d) && chmod 700 "$D"
S="$D/prover.sock"

# A test SRS is generated in-process. It is insecure: use --srs for real keys.
$P/midnight-gpu-proverd --insecure-test-srs --socket "$S" &

# The socket opens after the SRS and the key are ready. Wait for it.
for i in $(seq 1 120); do
  $P/midnight-gpu-prover-client --socket "$S" health && break
  sleep 1
done
$P/midnight-gpu-prover-client --socket "$S" health || exit 1

# 96 bytes: three canonical little-endian BLS12‑381 scalars. Mode 600.
head -c 96 /dev/zero > in.bin
chmod 600 in.bin
# --no-fallback: fail if the daemon does not serve the proof.
$P/midnight-gpu-prover-client --socket "$S" prove in.bin proof.bin --no-fallback --insecure-test-srs

$P/midnight-gpu-prover-client --socket "$S" stop

In a container

The image builds on a host without a GPU and without a CUDA install, because the CUDA toolkit comes from the builder image. The GPU enters the container through CDI, and the SRS is mounted read-only. 

docker buildx build -f gpu-prover/container/Dockerfile -t midnight-gpu-prover:local .

# Generate the CDI spec once, and again after every driver update.
sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml

# run-gpu.sh rejects a missing or unreadable spec and a spec whose host paths are missing;
# for WSL driver paths it also rejects a driver directory that does not match the live one.
SRS=bls_midnight_2p17   # the name of your SRS file
docker volume create midnight-gpu-prover-socket
gpu-prover/container/run-gpu.sh docker run -d --name midnight-gpu-prover \
  --device nvidia.com/gpu=all \
  --restart on-failure:3 \
  -v /path/to/srs:/srv/midnight/srs:ro \
  -e MIDNIGHT_GPU_PROVER_SRS="/srv/midnight/srs/$SRS" \
  -v midnight-gpu-prover-socket:/run/midnight-gpu-prover \
  midnight-gpu-prover:local

cargo test -p midnight-gpu-prover --all-features runs the CPU-path tests: admission arithmetic with fake device memory, the protocol, the queue, the fallback labels, the circuit breaker and verify-before-return. Every feature compiles with --all-features on a machine without CUDA.

The full steps are in the crate readme and the container readme.

The hook contract

Every hook obeys the rules below, which the architecture document states in full. They are what keep a proof from the GPU path equal to the proof of the CPU prover for the same witness and the same random values.

  1. The stock value, or a decline. A hook returns exactly the group element or the vector that the CPU routine returns for the same input. There is no approximate result and no third outcome.
  2. A decline leaves the input unchanged. When a hook declines, the CPU routine runs on the same buffers, with the same content, as if the hook did not exist. A hook can decline for any reason: an unsupported size, too little device memory, a device error.
  3. No randomness and no transcript access. A hook draws no random value and reads or writes no transcript state. If it accepts the call, its return value depends only on the arithmetic input.
  4. Every decline is counted. The device path counts each decline and the daemon reads the counters, so a proof that used the CPU for part of its arithmetic shows up in them.

The zero-knowledge argument

A proof from the GPU path has the same distribution as a proof from the CPU prover. After a request, the daemon zeroes and frees every device buffer and every staging buffer that held witness-dependent values, and it takes no further request unless it can confirm that.

Where the randomness is

A KZG commitment in midnight-proofs has no hiding scalar. Zero knowledge comes from random values that the prover writes into the polynomials themselves:

  • the blinding rows of the advice columns, except columns that a circuit declares unblinded;
  • the blinding rows of the LogUp multiplicity and aggregator columns;
  • the blinding rows of the permutation products;
  • two random values at each boundary between quotient limbs.

The blinding rows come from the RNG that the caller passes to the prover. The advice values are written right after synthesis. The others are drawn on one thread before the parallel work that uses them. The limb values come from the operating system RNG. All of this is stock code, and it runs on the CPU.

Why the hooks cannot change the distribution

A hook is deterministic arithmetic. For a given input it returns exactly the value that the CPU routine returns, or it declines and leaves the input unchanged. It draws nothing and does not see the transcript. The prover draws its blinding values and runs every transcript operation on the CPU, in the stock order. Circuit code can draw more randomness of its own on the host, as the foreign-curve chip does. The hooks draw none. For the same witness and the same random values, the transcript, the challenges and the proof bytes are therefore those of the CPU prover.

A caller seed alone does not fix the proof bytes, because the limb values come from the operating system RNG. The Lean oracle of the specification proves the same property for the model: any two devices that obey the hook contract give the same transcript and the same number of random draws.

The skew mask is not a blinder

The MSM backend computes

MSM(s) = MSM(s + r) − MSM(r)

with a fixed public vector r. The identity holds because an MSM is linear in its scalars. The purpose is to balance the bucket loads: a column with many equal values would put most points into a few buckets. The mask is public, so it hides nothing, and the argument above does not rely on it.

What crosses back from the device

The readback from the device is limited to the result point of each MSM, the partial bucket sums of the MSM kernel, the outputs of the transforms on the base domain (n values each, written into the caller's buffer), the coefficients of the quotient, and counters. The bucket sums are an intermediate of the vendored MSM: it copies them to the host for the final accumulation, counts the transfers and zeroes the host copies after use. The stock prover computes the same arithmetic results at the same points. The counters are extra: the daemon collects them for its request report. The numerator stays on the device: the division by the vanishing polynomial and the inverse transform run there, and no vector on the extended domain returns to the host.

What stays after a request

The daemon serves many witnesses, so residue matters. Before it takes the next request it overwrites with zeros, and then frees, every device buffer and every staging buffer that held witness-dependent values. The copies that may stay on the device are proving-key polynomials, which are public. On the host, the feature gpu keeps the quotient coefficients and the blinded limbs in owners that zero their whole allocation on release, on the device path and on the CPU path alike.

The trust boundary

The device, its driver and the host that runs the daemon sit inside the trust boundary, as the host does for the CPU prover. During a request the device holds witness-dependent vectors in the clear, so the design trusts whoever can read device memory while a request runs, as the CPU prover trusts whoever can read host memory. The wipe covers the time after a request: once the cleanup is confirmed, the witness-dependent device and staging buffers of the request are zeroed and freed. If the cleanup cannot be confirmed, the daemon retires. A daemon that crashes before the cleanup can leave witness data in device memory. On the host, the quotient coefficients and limbs are zeroed on release. The decoded witness, the other buffers of the stock prover and the intermediates of the stock quotient path are freed without zeroing, as on any CPU prover. The socket is local and owner only.

The oracle and the checks

The specification exists in forms that check each other. The requirements say what must hold. A Lean 4 oracle states the reference arithmetic and the request state machine and proves theorems about them. A Quint model of the state machine, written from the requirements and the design only, produces traces that are replayed through the oracle. Rust tests run the hooks against vectors that the oracle writes.

The check results need JavaScript and an HTTP server.

The theorems are about the models. That the code obeys the hook contract is a separate claim, and the Rust tests carry it: the vectors go through the CPU routine, the stub and the device hook, and faults are injected after upload and after launch.

Batch proving

midnight_proofs::gpu::batch::prove_batch proves several circuits concurrently in waves sized by device memory, and the batch session of midnight-gpu gives an admitted batch the device backend to itself. After each batch MSM the MSM contexts are evicted and checked, and after each transform or quotient the shared scratch, bounce and read-back buffers go through the wipe path. A proof made in a batch is byte-identical to the same proof made alone with the same randomness. The daemon does not use the batch path: it proves one request at a time, one more request waits in the queue, and a further one gets busy at once.

The proving pipeline

A proof is a fixed sequence of steps. The GPU path changes only where the hooked arithmetic runs. The sequence, the random draws and the transcript stay those of the CPU prover.

The NTT butterfly

The number-theoretic transform turns the coefficients of a polynomial into its values at the powers of a root of unity ω, an element of order exactly n. The radix-2 transform shown here is a bit reversal followed by log₂ n stages of butterflies. The animation runs it on 8 points of a small field so that every number can be checked by hand.

MSM bucket accumulation

A commitment is a multi-scalar multiplication: the sum of sᵢ·Pᵢ over all scalars sᵢ of a column and the SRS points Pᵢ. The bucket method replaces most of the scalar multiplications with additions. The animation uses six terms and 6-bit scalars in a toy group of order 61, where every point is a known multiple of a generator G.

Host and device memory, and the wipe

The daemon keeps public key material between requests. When a request ends, it overwrites with zeros every device buffer and every staging buffer that held witness-dependent values. The animation follows one request, then a second request on a device that another program also uses.

The fallback path

Every level has a CPU path: the build, the start of the daemon, each hook call and the client. A hook that declines hands its arithmetic back to the CPU routine. Before a proof starts, the daemon climbs an admission ladder (shown here for a native Linux host), a fixed order of memory checks that ends on the CPU. Whatever path a proof took, it leaves only after the verifier accepts it. The animation follows one hook call, the admission ladder and a client that cannot reach the daemon.

Operations

The daemon detects a CUDA device at run time and listens on a local Unix socket with mode 0600, where it serves only peers with its own user id. It serves one proof request at a time. One more waits, and a third gets busy at once. The resident policy, the admission wait, the memory margin, the thread count and an optional device lock are settings, each with a default in the crate readme. With no usable device the daemon still serves proofs, on the CPU.

Every proof carries a label. cpu means that the device served no call, and cpu-fallback that the client proved in its own process. After at least one served call, the label is gpu-degraded when the request counted a fallback, and gpu otherwise. A hook falls back for a lack of memory, a device error, a fault, an input that is not reduced, or a shape the device does not take. A request-level fallback, such as a hang-up or a lost lock lease, also counts, with the phase request. A degraded admission, which moves phases off the device as the evict step of the ladder does, is not a fallback: with a served device call and no counted fallback, the proof is labelled gpu, and the admission reasons are listed in degraded_reasons. Two declines are expected and leave a proof unmarked: a call below the minimum size, and no device. In acceptance mode the daemon fails a request with a degraded admission or a fallback.

The reply also holds the decline counts of the hook contract by phase and reason, the device peak of the request and the SHA-256 of the proof. The device-call counts, the decline counts, the wipe totals and the device peak are those of the request; a request that is admitted to the CPU reports a device peak of 0 and no wipe of an earlier request. The reply holds no witness value, no key and no seed. A request line that is valid UTF-8 but not a request of the protocol gets the error bad-request with the fixed text not a valid request; the reply does not echo the field name, the value or the path the caller sent. A line that is not UTF-8, and other framing failures, get bad-request with their own fixed text.

A benchmark of the GPU path turns off the client fallback, requires the label gpu, and reads device_calls for each operation to establish what ran on the device.

In a container, the image runs the daemon as a non-root user, mounts the SRS read-only and receives the GPU through the NVIDIA Container Toolkit or the Container Device Interface (CDI). Under systemd, an example unit runs the daemon as a service and restarts it on failure, with at most three starts in ten minutes. While the daemon is down, clients prove on the CPU. The build, the run commands and the unit are in the container readme.

Open items

The pull request is a draft. An independent audit of the backend is in progress, and the items below are not yet in the branch. They land as follow-up commits before the pull request is marked ready for review.

  • Intermediates of the stock quotient. The hook layer keeps the quotient read-back, its check-mode copies and the pieces of h in owners that zero their whole capacity on drop. The intermediates of the stock quotient path, which the decline path and check mode run, are still plain vectors: the coset clones in compute_nu_poly, the resize in coeff_to_extended and the vector of extended_to_coeff.
  • MSM bucket memory. The constructor of the vendored MSM does not zero its bucket allocation. The production wrapper masks its scalars; the tree also holds a test probe that runs an unmasked sparse MSM on a reused context. The zeroing at construction waits for a run in this tree that shows an unwritten slot.
  • Oracle citations. Two citations from a requirement to a theorem are too strong. GPU-078 cites acceptance_degraded_refused without its confirmed-wipe condition, so a request can finish with a fallback and a wipe error and get no degraded refusal. GPU-058 cites pin_wsl_budget for replacing both memory readings, but its input exercises only the first admission branch.
  • Async wipe release. A block that is zeroed, has its free enqueued and then fails the stream synchronisation is neither quarantined nor visible in pending_erasure().
  • Unsafe-code audit. Items UNSAFE-22, UNSAFE-23, UNSAFE-28 and UNSAFE-31 were open in the audit of the unsafe code and are not yet checked against this branch.

Other notes

  • A drain that fails. When a recorded drain cannot confirm a stream, the CUDA core keeps the affected staging and read-back buffers and hands out no new host buffer. The device-owner thread then, before it runs anything else, disables the device, tries again to zero the quarantined blocks, and attempts one reset of the CUDA context. A successful reset ends every transfer, clears the quarantine and counts the quarantined blocks whose zeroing stayed unconfirmed as lost unerased. A failed reset leaves the device disabled, keeps the quarantine records and leaves the unconfirmed drains outstanding. Every later call declines; a call that reaches the retired-device check records teardown, and calls queued for the device when the teardown starts decline with teardown unrun. No test yet covers a failed reset. pending_erasure() counts the unconfirmed drains until a successful reset settles them. The library never exits, and the daemon does not read pending_erasure() yet.
  • Static teardown. The device list of the vendored code lives behind a pointer that is never destroyed, and its NTT tables are owned and freed by teardown_ntt_tables() on the device-owner thread. This removes the exit-time destructors of the vendored code. The daemon does not call the table teardown yet; at exit the driver releases the tables.
  • Error paths. Failed staged and direct copies run an error drain before they return. Failures of a device wipe or of a release have their own erasure accounting. The MSM error arms of the vendored code drain every stream and stop C++ exceptions at the C entry points. The MSM collector waits for every worker it started, and each worker and the collector scrub a 64 KiB stack region. The device fault tests check the drains, the exception handling and the recovery; the stack scrub was checked by reading the source.
  • The staging size is an atomic value. A device test polls it from a second thread while staged copies run; a data race is not deterministic, so this test is weak evidence. The kernel field arguments are copied with memcpy, and the error path frees the owned message of the vendored code.
  • The quarantine report, pending_erasure(), gives counts and bytes. It counts the blocks of the vendored code whose zeroing is unconfirmed apart from the zeroed blocks that wait for their free, and the device regions of the Rust crate apart from both. It also counts the quarantined blocks whose zeroing was still unconfirmed when a reset succeeded; the live buffers that the reset releases are not in that count. It reports the outstanding unconfirmed drains apart. It does not name a single block. A public buffer whose free failed is quarantined and retried like a witness buffer.
  • With the feature gpu on, MockProver failure text, the debug output of the dev types and the tracing floor planner print <withheld> in place of assigned cell values. With the feature off, they print values as before. The stock floor planners still put Constant(<value>) in assignment annotations outside the dev tools; that is left as a suggestion for upstream.
  • At the pinned versions, the zkir library logs private inputs at error level on malformed-witness paths, under the target midnight_zkir, when a tracing subscriber is installed. The stock proof server filters only zkir. The benchmark wrapper turns off both targets, and the daemon installs no subscriber. The security document gives the operator setting.
  • The stock proof server 9.0.1 binds all interfaces and has no bind option. The benchmark runs it in a loopback-only network namespace behind a Unix socket.
  • Two teardown tests have no run against the code before the fix: the second test in gpu/tests/teardown_lost.rs, and the device test that holders of a device pointer make no CUDA call after the reset.
  • The Quint model was checked by simulation and trace replay. Exhaustive model checking is future work.
  • The new CI workflows have not yet run on a GitHub runner. Their steps pass when run locally.
